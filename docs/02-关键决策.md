# 关键决策

这份文档记录"为什么这么选"，包括被否掉的方案。目的是让后来者（或三个月后的自己）不用重新踩一遍。

---

## 一、上游项目怎么选

现有四个公开项目，能力不重叠，也都有明显的不可用之处：

| 项目 | 能提供什么 | 结论 |
|---|---|---|
| [lvmaple/minas_plugin](https://github.com/lvmaple/minas_plugin) | 插件源码 + 统一部署工具 + **1.0.9.462 的 root 工具**（新链路） | **主体采用** |
| [xuchen96/xiaomi-nas-guide](https://github.com/xuchen96/xiaomi-nas-guide) | SSH 持久化：systemd 单元、开机钩子思路 | **采用**（修补方案） |
| [kid0114/xiaomi-nas-ssh-root-tool](https://github.com/kid0114/xiaomi-nas-ssh-root-tool) | 双钩子原理、`/data/etc/upper` 镜像复制 | **仅参考原理**，二进制补丁弃用 |
| [scruel/xiaomi-storage-minas-tool](https://github.com/scruel/xiaomi-storage-minas-tool) | WebDAV 视频分段注入链 | **排除**，462 起已被修补 |

结论：**不是照搬任何一个，而是取各家可用部分 + 自己补编排层。**

kid0114 的二进制补丁为什么弃用：它绑定 1.0.8.425 的旧文件（要匹配旧字节序列），在 464 上根本对不上。xuchen96 的"就地替换字符串"方案不依赖版本，更稳。

scruel 的注入链为什么排除：它的入口是 WebDAV 视频分段的路径处理缺陷，462 已修补。在 464 上跑只会失败——**而且会在设备上留下失败痕迹**（临时账号、暂存目录）。

## 二、六个设计冲突

融合时遇到的真正困难不是"哪个方案好"，而是两个都对的方案互相打架。逐条记录。

### C1 · dropbear 怎么改：换二进制 vs 改字符串

| 方案 | 优点 | 缺点 |
|---|---|---|
| kid0114：用旧版完整二进制替换 | 简单 | 绑定 1.0.8.425，464 上不可用；替换整个二进制风险更高 |
| xuchen96：就地替换 `/usr/sbin/mi-shell` → `/bin/bash` | 不依赖版本；只动 18 字节 | 必须严格等长，错了就砖 |

**选后者**，并加两道保险：替换前检查 `mi-shell` 恰好出现 1 次；写完后用 `strings | grep /bin/bash` 复核。加固措施是**先写副本到 `/data/minas-ssh/dropbear`**，永远不改 `/usr/sbin/dropbear` 原件——出问题最多是我们自己的服务起不来，原厂组件不受影响。

### C2 · 部署通道：修好 SSH ≠ 能用 scp

"SSH 能连上"和"能传文件"是两件事：

- 原厂 dropbear **没有 `sftp-server`**，新版 OpenSSH 的 `scp` 默认走 SFTP 协议 → 直接失败
- 更早一步：认证虽然通了，但 exec 通道被 mi-shell 拦住，命令无输出

**结论：分两段走。**

```
第 1 段（SSH 固化前）：走 2323 socat root shell，纯 socket 送脚本
第 2 段（SSH 固化后）：用 scp 正常传文件
```

固化后能 scp，是因为我们换上了修补版 dropbear（shell 是 bash）+ 服务端支持传统 scp 协议。若读者的 OpenSSH 太新，加 `-O` 走旧协议。

### C3 · 定时机制：cron vs systemd timer

上游和经验帖都用 `crontab`。但这台设备上 **`crontab` 不生效**——厂商的精简系统没有启用 cron 守护进程，写了也白写（root 工具自己用的是 `/etc/crontabs/root` + 厂商 cron，属于特例）。

**选 systemd timer**，额外拿到三个 cron 没有的能力：

- `Persistent=true`：错过的时间点开机后补跑（关机期间被破坏也能自愈）
- 日志直接进 `journalctl -u keep-plugins.service`
- 多个 `On*` 单位共存，取最早触发的

### C4 · 插件运行时放哪：`/home` vs `/data`

`/home/<uid>/plugin/<id>` 是厂商**有权重建**的目录——这正是"重启丢插件"的直接原因。

**迁到 `/data/minas/plugins/<id>`**，`/home` 保留副本供单文件部署工具使用，网页目录做软链。代价是要维护两份，收益是厂商清 `/home` 时服务不中断。

### C5 · 插件保护：事后修复 vs 事前拦截

| 方案 | 结果 |
|---|---|
| 定时器发现被删 → 重新安装 | **失败**。卸载发生在对账过程中，等发现时服务、注册表、目录都被拆了，重装要断服务 |
| 目录守卫在源头合并目录 | **有效**。对账时"云端有它"，卸载动作根本不触发 |

**选守卫**，并把它做成 fail-closed：云端异常时返回 503 让 `plugincenter` 放弃更新。这是整个项目最重要的一条取舍——**"不更新"是可恢复的，"删插件"不是**。

### C6 · 开机钩子：`restart` vs `start`

早期钩子写的是 `systemctl restart minas-sshd`。结果：存储池每次重挂载（插拔硬盘、定时任务）都会触发钩子 → 干掉正在用的 SSH 会话。表现为"用几分钟就断"。

**改成"只在 inactive 时 start"**：`is-active || start`。钩子的职责是"补"，不是"重来"。

## 三、本项目的原创部分

上游只解决"装一次"，没解决"活下来"。以下六件事是上游没有的：

1. **参数化配置**：一份 `config.json` 生成 NAS 侧 `plugins.json` + 上游 `deploy-config.json`，代码里零设备常量（便于开源与换机）。
2. **免 WSL 通道**：socket 直连 2323，运行时给上游打补丁（不改上游源码），并补上 Windows 下失效的清理通道。
3. **写预演**：花 3 秒验证注入链第一环，避免在已修补的固件上白跑一遍、留下垃圾。
4. **目录守卫**：对账删除的根因解法。
5. **运行时迁移**：把服务从厂商可重建的目录里搬出来。
6. **调度管理 `keepctl`**：不改 systemd 文件就能调间隔/日历/开关，并修掉了 timer 重启后不调度的经典坑（只配 `OnUnitActiveSec` 时缺少计时起点，补 `OnActiveSec=30s`）。

## 四、明确不做的事

- **不做降级**。设备有防降级机制（RPMB 门控），承诺不了。
- **不打包第三方二进制**。上游的 `.so` 与插件代码按需拉取，本仓库只放编排层——既是许可问题，也避免"作者替读者承担二进制风险"。
- **不自动跨大版本固件**。新固件需要重新评估，工具的 `probe` 与 `write_probe` 只负责告诉你"这条链还在不在"。
- **不做静默升级**。`Persistent=true` 会补跑，但不会在部署时自动改设备行为。
