# 故障复盘

四个真实故障。每个都遵循同一个结构：**现象 → 怎么定位 → 根因 → 修法 → 教训**。

写下来的目的不是记录功劳，是记住"下一次别再从现象开始猜"。

---

## 事故 A · 重启后插件全丢

### 现象

部署当天一切正常。重启设备后，三个插件的端口全部不监听，App 里显示未安装。手动启动服务能起来，再重启又没了。

### 定位

三次重启对照，逐步缩小范围：

1. 重启前记录 `/home/<uid>/plugin/<id>/INFO`、`ports` 表、systemd 单元、端口监听
2. 重启后立刻比对
3. 发现三件事同时发生：目录存在但服务不启动；`/tmp/<plugin>` 目录消失；`ports` 表里没有插件条目

### 根因（三个叠加）

**① `ports` 表未登记**
`/etc/config/plugin` 里的 `ports` 是厂商的插件注册表。没登记的插件，在厂商重建插件目录时会被当成"未知残留"清掉。

**② `/tmp` 是 tmpfs，重启即空**
服务单元把 stdout 重定向到 `/tmp/<plugin>/server.log`。重启后目录不存在 → 打开失败 → 服务启动失败 → `Restart=on-failure` 每 5 秒重试 → 无限崩溃循环。日志里只能看到 `status=1/FAILURE`，看不到"目录不存在"。

**③ `restore.sh` 的 flock 自死锁**
上游的 `restore.sh` 会加一个共享锁 `flock`。我们的自愈脚本也调它，导致自己等自己——进程挂住不退出，看起来像"自愈没生效"。

### 修法

| 根因 | 修法 |
|---|---|
| ports 未登记 | 自愈每轮检查并按 `plugins.json` 重写 `ports` 表 |
| /tmp 日志目录 | 自愈每轮 `mkdir -p /tmp/<plugin>`；开机钩子也建一次（双保险） |
| flock 自死锁 | **不再调 `restore.sh`**，自愈自己实现所需逻辑；锁文件改用独立路径 |

### 教训

> 服务的 `Restart=on-failure` + 一个不可写路径 = 静默崩溃循环。**任何 `Restart=` 的服务，先确认它依赖的路径在重启后一定存在。**

## 事故 B · 运行中插件突然消失（最隐蔽的一个）

### 现象

不是重启后，是**用着用着**插件就没了。SSH 上去看，服务单元被删、`/home` 目录被删、App 显示未安装。日志里有 `already taken down`。

### 定位

第一次发生时以为是自愈脚本 bug，加了日志。第二次复现后，日志给出了时间线：

```
22:59  plugincenter: plugin dockerctl already taken down
22:59  preuninstall → uninstall → postuninstall
23:13  同样的事情再来一次
```

对照 `plugincenter` 的行为：它定时（以及 App 打开应用市场时）拉云端 `server.list` 做对账。自研插件不在云端目录里 → 判"已下架" → 执行卸载。

### 根因

**这不是 bug，是厂商的正常逻辑。** 任何不在官方目录里的插件，都会被对账删除。

之前的 v3 方案试图用自愈"事后补回来"——但卸载是原子动作（拆单元、删目录、清注册），补回来要重建一切，期间服务是断的。而且对账很频繁，补一次删一次。

### 修法

v4 引入**目录守卫**：把 `plugincenter` 的目录源改成 `127.0.0.1:9310`，守卫代理云端请求并把自研插件合并进响应。

三条约束，缺一条都会重新引入故障：

1. **fail-closed**：云端不可达返回 503。若返回"空目录"，`plugincenter` 会认为"所有插件都被下架"，一次性删光。
2. **响应形状校验**：结构不符合预期就 502，不猜。
3. **只合并缺失项**：云端已有的插件不动，避免覆盖官方元数据。

### 验收方式

不是"看起来没事"，而是**主动触发一次真实对账**：

```bash
plugincenter -u <user> update      # 走守卫 → 云端 → 合并全链路
# 断言：条目仍在、MainPID 未变、日志无 taken down
```

连续两次零卸载，才算通过。

### 教训

> 与厂商组件抢资源时，**事后修复永远打不过事前拦截**。找到那个"决定要不要删"的判断点，在它前面插一脚。

## 事故 C · App 里显示"需要下载"，点了又失败

### 现象

插件在应用市场里能看见，但状态是"下载"而不是"打开"。点击下载，提示安装失败。

### 定位

`plugincenter` 判断"已安装"看的是 `/data/plugin/<user>.list` 里的 `install` 字段。实测三个插件是：

```
install=False  status=free
```

再看条目的 `mpk` 字段——指向**本地路径**（`/home/.../INFO`），不是真实下载地址。所以：

- 状态错 → 显示"下载"
- 点下载 → 去解一个不存在的 URL → 失败

为什么会变成 `False`？因为 `plugincenter` 每次从（守卫合并后的）目录重建清单时，会把"新出现"的条目按**默认值**初始化。

### 根因

v4 的自愈只补**缺失**的条目，不修正**已存在但状态被重置**的条目。于是错误状态一直残留。

### 修法

自愈增强为：条目已存在时，用缓存条目覆盖 10 个状态字段（`status`、`install`、`upgrade`、`enable`、`online`、`autograde`、`icon`、`progress`、`frontend`、`changetime`）。

改完立即验证两件事：

1. 手动跑一次自愈 → 三个插件变 `install=True / status=running`
2. **主动触发一次 `plugincenter update`** → 状态不被重置（证明抗对账）

第二条是关键。只验证第 1 条会得出错误结论——因为对账会再覆盖回去。

### 教训

> "显示不对"往往不只是显示问题。顺着 UI 状态往下挖，通常能挖到一个真实的功能故障。**验收要跑完整链路，不要只跑修的那一步。**

## 事故 D · 定时器改完隔一会儿就不跑了

### 现象

`keepctl off` 再 `keepctl on` 之后，`systemctl list-timers` 的 `NEXT` 变成 `n/a`，等了 21 分钟一次都没跑。

### 根因

timer 里**只配了 `OnUnitActiveSec`**。这个指令的含义是"上次运行结束后 N 时间再跑"——它需要一个**参照点**。timer 刚启动时没有"上次运行"，于是永远在等一个不会到来的起点。

这是 systemd 的经典坑：`OnUnitActiveSec` 单独使用时，timer 重启后会失速。

### 修法

加一行 `OnActiveSec=30s`：timer 启动 30 秒后先跑一次，建立参照点，之后 `OnUnitActiveSec` 才有意义。

```ini
[Timer]
OnBootSec=90s            # 开机 90 秒后
OnActiveSec=30s          # timer 启动 30 秒后（建立基准）
OnUnitActiveSec=2min     # 之后每 2 分钟
Persistent=true
```

### 验收

`off/on` 循环 + 等 35 秒 + 查 `NEXT` 不为 `n/a`。这个回归测试后来固化成了 `keepctl` 的一部分。

### 教训

> 改调度策略后，**必须看 `NEXT` 有没有值**，而不是看 `is-active`。`active` 只说明 timer 进程活着，不说明它在调度。

## 防御性措施汇总

这些教训被固化进了代码，不是写在文档里就完了：

| 教训 | 落地 |
|---|---|
| 不可写路径 + Restart = 崩溃循环 | 自愈每轮建 `/tmp/<plugin>`；钩子也建一次 |
| 事后修复打不过事前拦截 | 目录守卫 fail-closed |
| 状态位会被对账重置 | 修 10 个字段，且验收要跑真实对账 |
| 只配 `OnUnitActiveSec` 会失速 | 加 `OnActiveSec=30s`；`keepctl` 打印 `NEXT` |
| 钩子 `restart` 会踢掉活跃会话 | 改成 `is-active || start` |
| 等长替换错了会砖 | 出现次数必须为 1，否则不写补丁；只写副本不改原件 |
